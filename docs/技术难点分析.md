# 技术难点分析

> 校园快修服务助手 —— 核心技术难点与对策
> 版本：v1.1
> 说明：依据《第10组-校园快修助手需求分析文档》V1.0 同步更新。本文档分析系统实现过程中的关键技术难点，作为开发优先级、技术选型和评测指标的依据。

---

## 1. 多模态理解的分诊准确率

### 难点描述
学生输入“一句话 + 一张照片”，系统需要同时输出：
- 故障类别（关联 `repair_category`，如水电 / 网络 / 家具 / 其他）
- 楼栋、房间号
- 紧急程度（`emergency_level`）
- 预约时间（`appointment_time`）

字段多、易遗漏、大模型容易产生幻觉（编造不存在的位置）。

### 技术方案
1. 使用 **Function Calling / JSON Schema** 强制大模型按固定格式输出。
2. 楼栋、房间号**优先用正则从文本中抽取**（如“3号楼302”），LLM 只做兜底。
3. 照片仅用于**类别判断**（如水管爆裂 vs 灯不亮），不做具体位置识别。
4. 预约时间由学生选择，系统只校验“必须晚于当前时间”，**不交给 LLM 生成**。
5. AI 返回后写入 `repair_order.ai_parsed_info`，便于回溯。
6. 类别最终关联 `repair_category`，非法类别回落为 `OTHER` 并提示学生确认。

### 风险与对策
| 风险 | 对策 |
|------|------|
| LLM 输出的类别不在枚举内 | 输出后做白名单校验，非法值回落到 OTHER，并提示学生人工确认 |
| 楼栋识别错误 | 正则优先，正则失败再交给 LLM；仍失败则要求学生手动填写 |
| 照片识别慢 | 异步处理，先存原始工单，AI 结果回填；AI 超时不能阻塞工单提交 |
| 紧急程度误判 | `emergency_level` 只允许 LOW / MEDIUM / HIGH，学生可修正 |

### 评测指标
- **分诊准确率** = 类别预测正确数 / 测试集总数，目标 **≥ 85%**
- 测试集：人工标注 100 条“描述+照片→正确类别”样本

## 2. RAG 问答的知识库质量

### 难点描述
- 维修手册 + 历史工单格式不统一，切块策略直接影响召回率。
- “能自修就分流”的判断标准模糊，容易误导学生。
- 向量检索相似度阈值难定。

### 技术方案
1. 知识库统一存入 `knowledge_base`，按**故障类别、故障现象、答案**组织。
2. 手册与历史工单来源分别标记为 `MANUAL / ORDER`。
3. 向量库选 **Chroma**（轻量、本地部署、免运维）。
4. 检索相似度 **< 0.7** 时不硬答，转引导报修。
5. RAG 回答中必须携带**引用来源**，便于验证。
6. 学生反馈 `is_solved=true` 的会话用于统计自修解决率。

### 风险与对策
| 风险 | 对策 |
|------|------|
| 知识库内容过时 | 定期从已完成工单的 `repair_order.result` 中补充，管理员审核后入库 |
| 相似度阈值定错 | 用 20~30 条真实问题做回归测试 |
| 答非所问 | 低相似度不答，直接转报修入口 |
| 知识污染 | 评分 < 4 或未审核结论不得进入 `knowledge_base` |

### 评测指标
- **自修解决率** = `is_solved=true` 的会话数 / 总会话数，目标 **≥ 30%**
- **分流正确率** = 该自修的分到自修 + 该派单的分到派单 / 总数，目标 **≥ 85%**
- **知识入库率** = 审核通过数 / 候选数，目标 **≥ 60%**

## 3. 调度 Agent 的冲突检测

### 难点描述
- 师傅同一时间段不能被派两单。
- 故障类别要匹配师傅专长。
- 位置要就近。
- 负载要均衡。
- 改约后需要重新派单。

### 技术方案
**不要真上 LLM Agent**（不稳定、慢、贵），用**规则引擎 + 加权打分**：

匹配得分 = 专长匹配 × 0.4  
　　　　 + 时间窗匹配 × 0.3  
　　　　 + 距离（楼栋接近度）× 0.2  
　　　　 + 师傅当前负载 × 0.1

流程：
1. 读取 `repair_order` 的类别、楼栋、预约时间、紧急度。
2. 查询 `worker_schedule`，筛选当天时间段匹配且状态为 `FREE` 的师傅。
3. 过滤掉时间冲突、`cur_orders >= max_orders` 的师傅。
4. 对剩余师傅打分。
5. 选最高分师傅，将 `worker_id / assign_score / assign_reason` 写入 `repair_order`，状态改为 `ASSIGNED`。
6. 更新 `worker_schedule.cur_orders`。
7. 若无人可派，工单保持 `SUBMITTED` 并通知管理员。
8. 改约时进入 `RESCHEDULED`，然后重新触发派单。

### 风险与对策
| 风险 | 对策 |
|------|------|
| 并发派单冲突 | 派单操作加数据库行锁或乐观锁；版本冲突时重新读取并重试，最多 3 次 |
| 所有师傅都忙 | 工单保持 SUBMITTED，提供“加急单”标记，管理员手动干预 |
| 打分权重不合理 | 上线后根据实际派单接受率调参，权重可配置 |
| 改约导致重复派单 | 改约后先清理旧派单信息，再重新走调度 |

### 评测指标
- **派单成功率** = 成功派单数 / 总工单数，目标 **≥ 90%**
- **平均响应时长** = 从提交到师傅接单的时间

## 4. 状态机的幂等可靠

### 难点描述
- 用户连点“接单”、网络重试、并发改约。
- 状态乱序（如从“已完成”回退到“处理中”）。
- 旧状态名与需求文档不一致，必须统一。

### 技术方案
1. **状态前置校验**：只允许白名单内的状态流转。
2. **幂等键**：前端提交时生成 UUID 作为 `idempotency_key`，后端唯一索引。
3. **乐观锁**：`repair_order` 加 `version` 字段，更新时校验版本。
4. **状态变更必写日志**：每次状态变更都写 `order_status_log`，可追溯。
5. 终态 `COMPLETED / CANCELLED` 不允许再流转。
6. `RESCHEDULED` 是改约中间态，只允许流向 `ASSIGNED / SUBMITTED / CANCELLED`。

### 新状态机
```text
SUBMITTED（待派单）
├──► ASSIGNED（已派单）──► ON_THE_WAY（上门中）──► PROCESSING（处理中）
│        │                                              │
│        └──► RESCHEDULED（已改约）──► ASSIGNED / SUBMITTED / CANCELLED
│                                                       ▼
│                                              PENDING_ACCEPT（待验收）
│                                                       │
│                                                       ├──► COMPLETED（已完成，终态）
│                                                       └──► PROCESSING（驳回返修）
└──► CANCELLED（已取消，终态）
```

### 风险与对策
| 风险 | 对策 |
|------|------|
| 重复提交 | `idempotency_key` 唯一索引拦截 |
| 并发更新 | `version` 乐观锁 |
| 非法流转 | 状态机白名单校验，抛业务异常 |
| 状态日志缺失 | 状态变更与日志写入放在同一事务 |

### 评测指标
- 状态日志完整率 = 有日志的状态变更数 / 总变更数 = **100%**
- 重复提交拦截率 = **100%**

## 5. 知识沉淀的数据闭环

### 难点描述
- 评价完的工单结论，怎么“清洗”后进知识库？
- 直接自动回流会污染知识库，导致 RAG 越答越歪。

### 技术方案
1. 评分 **≥ 4** 且 `repair_order.result` 非空 → 进候选池。
2. 管理员在后台**人工审核**后才写入 `knowledge_base`。
3. 知识条目带来源标记（`MANUAL / ORDER`），并记录 `source_order_id`，可追溯。
4. 支持条目去重合并、有帮助计数、失效下线。
5. 保留回滚能力，记录每次回流。

### 风险与对策
| 风险 | 对策 |
|------|------|
| 低质量结论污染 | 人工审核 + 评分门槛 |
| 知识库膨胀 | 定期合并同类条目，去重 |
| 回流后 RAG 变差 | 保留回滚能力，记录每次回流 |
| 来源不可追溯 | `knowledge_base.source_order_id` 必须记录 |

### 评测指标
- 知识入库率 = 审核通过数 / 候选数，目标 **≥ 60%**
- 回流后分诊准确率变化

## 6. 前后端字段一致性与统一返回

### 难点描述
- 前后端字段名不一致导致联调困难。
- JPA 懒加载序列化报错。
- 错误码不统一。
- 需求文档已改为统一响应 `code=200`，旧文档 `code != 0` 需同步。

### 技术方案
1. 后端统一返回 `{ code, message, data }`，成功时 `code = 200`。
2. DTO 与 Entity 分离，避免直接序列化 Entity。
3. 前端 axios 拦截器统一处理 `code != 200` 的情况。
4. 字段命名：前端 camelCase，数据库 snake_case，由 JPA 自动映射。
5. 数据项设计先行，前后端共用。

### 风险与对策
| 风险 | 对策 |
|------|------|
| 字段对不上 | 数据项设计文档先行，前后端共用 |
| 懒加载异常 | DTO 转换时手动组装，或加 `@JsonIgnore` |
| 错误码混乱 | 定义统一错误码表，成功码为 200 |
| 状态枚举不一致 | 枚举以需求文档 6.4 为准 |

### 评测指标
- 联调返工次数 = 0（理想）
- 接口一次通过率 ≥ 90%

## 7. 运营看板、通知与数据权限

### 难点描述
- 看板需要聚合维修量、平均响应时长、平均完成时长、满意度、高频故障 Top 榜。
- 数据量达到 10 万工单时，看板查询要求 ≤ 3 秒。
- 状态变更后要发站内通知。
- 学生只能看本人工单，师傅只能看派给本人的工单，管理员才能看全局。

### 技术方案
1. 看板统计走只读查询或预聚合表，避免每次实时全表扫描。
2. 为 `repair_order.create_time / status / category_id / worker_id`、`order_evaluation.score` 建索引。
3. 高频故障 Top 榜按 `category_id` 和标题聚合。
4. 通知写入 `notification`，状态变更事务提交后发送，失败重试。
5. 权限采用 JWT + 角色接口鉴权，Service 层再做数据权限校验。
6. 学生查询工单必须带 `student_id` 条件；师傅查询必须带 `worker_id` 条件。

### 风险与对策
| 风险 | 对策 |
|------|------|
| 看板慢 | 预聚合、缓存、索引、限制时间范围 |
| 通知丢失 | 事务后发送，失败重试，站内信可补偿 |
| 越权查看 | 接口级鉴权 + Service 数据权限双重校验 |
| 看板数据不一致 | 明确统计口径，必要时离线聚合 |

### 评测指标
- 看板统计查询 ≤ 3 秒（10 万工单以内）
- 越权访问拦截率 = 100%
- 通知可查询、可标记已读

## 8. 难点优先级与开发顺序建议

| 优先级 | 难点 | 原因 |
|--------|------|------|
| P0 | 状态机幂等 | 所有功能的基础 |
| P0 | 前后端字段一致 | 联调效率 |
| P0 | 权限与数据隔离 | 安全需求，学生/师傅数据不能越权 |
| P1 | 多模态分诊 | 核心指标 |
| P1 | RAG 问答 | 核心功能 |
| P2 | 调度 Agent | 可用规则引擎降级实现 |
| P2 | 知识沉淀 | 后期迭代 |
| P2 | 运营看板与通知 | 管理端增强功能 |
