# 技术难点分析

> 校园快修服务助手 —— 核心技术难点与对策
> 版本：v1.0
> 说明：本文档分析系统实现过程中的关键技术难点，作为开发优先级、技术选型和评测指标的依据。

---

## 1. 多模态理解的分诊准确率

### 难点描述
学生输入"一句话 + 一张照片"，系统需要同时输出：
- 故障类别（水电 / 网络 / 家具 / 其他）
- 楼栋、房间号
- 紧急程度
- 预约时间

字段多、易遗漏、大模型容易产生幻觉（编造不存在的位置）。

### 技术方案
1. 使用 **Function Calling / JSON Schema** 强制大模型按固定格式输出
2. 楼栋、房间号**优先用正则从文本中抽取**（如"3号楼302"），LLM 只做兜底
3. 照片仅用于**类别判断**（如水管爆裂 vs 灯不亮），不做具体位置识别
4. 预约时间若学生未填，默认取"今天 14:00-18:00"，不交给 LLM 生成

### 风险与对策
| 风险 | 对策 |
|------|------|
| LLM 输出的类别不在枚举内 | 输出后做白名单校验，非法值回落到 OTHER |
| 楼栋识别错误 | 正则优先，正则失败再交给 LLM |
| 照片识别慢 | 异步处理，先存原始工单，AI 结果回填 |

### 评测指标
- **分诊准确率** = 类别预测正确数 / 测试集总数，目标 **≥ 85%**
- 测试集：人工标注 100 条"描述+照片→正确类别"样本

## 2. RAG 问答的知识库质量

### 难点描述
- 维修手册 + 历史工单格式不统一，切块策略直接影响召回率
- "能自修就分流"的判断标准模糊，容易误导学生
- 向量检索相似度阈值难定

### 技术方案
1. 手册按**故障类别**分块，历史工单按**维修结论**分块
2. 向量库选 **Chroma**（轻量、本地部署、免运维）
3. 检索相似度 **< 0.7** 时不硬答，转引导报修
4. RAG 回答中必须携带**引用来源**，便于验证

### 风险与对策
| 风险 | 对策 |
|------|------|
| 知识库内容过时 | 定期从已完成工单的结论中补充 |
| 相似度阈值定错 | 用 20~30 条真实问题做回归测试 |
| 答非所问 | 低相似度不答，直接转报修入口 |

### 评测指标
- **自修解决率** = is_solved=true 的会话数 / 总会话数
- **分流正确率** = 该自修的分到自修 + 该派单的分到派单 / 总数

## 3. 调度 Agent 的冲突检测

### 难点描述
- 师傅同一时间段不能被派两单
- 故障类别要匹配师傅专长
- 位置要就近
- 负载要均衡

### 技术方案
**不要真上 LLM Agent**（不稳定、慢、贵），用**规则引擎 + 加权打分**：

```
派单得分 = 专长匹配 × 0.4 + 时间窗匹配 × 0.3 + 距离（楼栋接近度）× 0.2 + 师傅当前负载 × 0.1
```

流程：
1. 过滤掉时间冲突的师傅（worker_schedule 表 + 已派工单时间窗交集）
2. 对剩余师傅打分，取最高分者
3. 更新工单的 `worker_id / assign_score / assign_reason`，置为 ASSIGNED，写 OrderStatusLog（不建独立派单表）
4. 若无人可派，工单回到 SUBMITTED 并通知管理员

### 风险与对策
| 风险 | 对策 |
|------|------|
| 并发派单冲突 | 派单操作加数据库行锁或乐观锁 |
| 所有师傅都忙 | 提供"加急单"标记，管理员手动干预 |
| 打分权重不合理 | 上线后根据实际派单接受率调参 |

### 评测指标
- **派单成功率** = 成功派单数 / 总工单数
- **平均响应时长** = 从提交到师傅接单的时间

## 4. 状态机的幂等可靠

### 难点描述
- 用户连点"接单"、网络重试、并发改约
- 状态乱序（如从"已完成"回退到"处理中"）

### 技术方案
1. **状态前置校验**：只允许白名单内的状态流转（见数据项设计 3.2）
2. **幂等键**：前端提交时生成 UUID 作为 `idempotency_key`，后端唯一索引
3. **乐观锁**：RepairOrder 加 version 字段，更新时校验版本
4. **状态变更必写日志**：每次状态变更都写 `OrderStatusLog`，可追溯

### 风险与对策
| 风险 | 对策 |
|------|------|
| 重复提交 | idempotency_key 唯一索引拦截 |
| 并发更新 | version 乐观锁 |
| 非法流转 | 状态机白名单校验，抛业务异常 |

### 评测指标
- 状态日志完整率 = 有日志的状态变更数 / 总变更数 = 100%
- 重复提交拦截率 = 100%

## 5. 知识沉淀的数据闭环

### 难点描述
- 评价完的工单结论，怎么"清洗"后进知识库？
- 直接自动回流会污染知识库，导致 RAG 越答越歪

### 技术方案
1. 评分 **≥ 4** 且维修结论非空 → 进候选池
2. 管理员在后台**人工审核**后才写入 KnowledgeItem
3. 知识条目带来源标记（MANUAL / HISTORY），可追溯

### 风险与对策
| 风险 | 对策 |
|------|------|
| 低质量结论污染 | 人工审核 + 评分门槛 |
| 知识库膨胀 | 定期合并同类条目，去重 |
| 回流后 RAG 变差 | 保留回滚能力，记录每次回流 |

### 评测指标
- 知识入库率 = 审核通过数 / 候选数
- 回流后分诊准确率变化

## 6. 前后端字段一致性与统一返回

### 难点描述
- 前后端字段名不一致导致联调困难
- JPA 懒加载序列化报错
- 错误码不统一

### 技术方案
1. 后端统一返回 `{ code, message, data }`
2. DTO 与 Entity 分离，避免直接序列化 Entity
3. 前端 axios 拦截器统一处理 code != 0 的情况
4. 字段命名：前端 camelCase，数据库 snake_case，由 JPA 自动映射

### 风险与对策
| 风险 | 对策 |
|------|------|
| 字段对不上 | 数据项设计文档先行，前后端共用 |
| 懒加载异常 | DTO 转换时手动组装，或加 @JsonIgnore |
| 错误码混乱 | 定义统一错误码表 |

### 评测指标
- 联调返工次数 = 0（理想）
- 接口一次通过率 ≥ 90%

## 7. 难点优先级与开发顺序建议

| 优先级 | 难点 | 原因 |
|--------|------|------|
| P0 | 状态机幂等 | 所有功能的基础 |
| P0 | 前后端字段一致 | 联调效率 |
| P1 | 多模态分诊 | 核心指标 |
| P1 | RAG 问答 | 核心功能 |
| P2 | 调度 Agent | 可用规则引擎降级实现 |
| P2 | 知识沉淀 | 后期迭代 |
