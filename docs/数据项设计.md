## 1. 实体总览

共 9 张业务表，与 `init.sql` 一一对应。

| 实体 | 中文名 | 所属功能 | 说明 |
|------|--------|----------|------|
| User | 用户 | 全角色 | 学生 / 师傅 / 管理员三类角色统一管理 |
| RepairCategory | 故障类别 | 智能报修 / 基础配置 | 故障分类，含“是否可自助解决”标记 |
| RepairOrder | 报修工单 | 智能报修 / 进度跟踪 | 核心业务实体，派单字段内嵌 |
| OrderStatusLog | 状态流转日志 | 进度跟踪 | 工单状态变更记录 |
| WorkerSchedule | 师傅排班 | 调度 | 师傅可服务时间、区域与负载 |
| KnowledgeBase | 知识库 | 自助诊断 | 维修手册 + 历史结论 |
| OrderEvaluation | 服务评价 | 评价与沉淀 | 工单完成后的评分与评价 |
| Notification | 通知消息 | 通知 | 站内通知 |
| DiagnosisSession | 诊断会话 | 自助诊断 | 扩展实体：需求文档 6.1 表总览未列，但 FR-02-08 与时序图要求，建议小组确认是否补充为第 9 张表 |

> 说明：
> 1. 旧 `Worker` 合并进 `User`，师傅专长用 `specialty`，状态用 `status`。
> 2. 旧 `Schedule` 改为 `worker_schedule`。
> 3. 旧 `Assignment` 不再单独建表，派单结果写入 `repair_order.worker_id / assign_score / assign_reason`。
> 4. 旧 `Evaluation` 改为 `order_evaluation`。
> 5. 旧 `KnowledgeItem` 改为 `knowledge_base`。

## 3. 状态机定义

### 3.1 工单状态（RepairOrder.status）

| 状态 | 中文名 | 说明 |
|------|--------|------|
| SUBMITTED | 待派单 | 学生已提交，等待调度 Agent 派单 |
| ASSIGNED | 已派单 | 已匹配到师傅，等待师傅接单 |
| ON_THE_WAY | 上门中 | 师傅已接单，正在赶往现场 |
| PROCESSING | 处理中 | 师傅正在维修 |
| PENDING_ACCEPT | 待验收 | 师傅维修完毕，等待学生确认 |
| COMPLETED | 已完成 | 学生确认验收（终态） |
| CANCELLED | 已取消 | 工单被取消（终态） |
| RESCHEDULED | 已改约 | 改约中间态，由已派单进入，改约后触发重新派单 |

### 3.2 允许的状态流转

| 原状态 | 允许流转到 |
|--------|-----------|
| SUBMITTED | ASSIGNED, CANCELLED |
| ASSIGNED | ON_THE_WAY, CANCELLED, RESCHEDULED |
| ON_THE_WAY | PROCESSING, CANCELLED |
| PROCESSING | PENDING_ACCEPT, CANCELLED |
| PENDING_ACCEPT | COMPLETED, PROCESSING（驳回返修） |
| COMPLETED | ——（终态） |
| CANCELLED | ——（终态） |
| RESCHEDULED | ASSIGNED（重新派单成功）、SUBMITTED（重新派单失败）、CANCELLED |

## 5. 数据流简述

1. **报修**：学生提交 → AI 多模态理解 → 补全 `category_id / building / room / emergency_level` → 生成 `RepairOrder`（`SUBMITTED`）→ 写 `OrderStatusLog` → 触发派单。
2. **诊断分流**：学生提问 → RAG 检索 `knowledge_base` → 命中且高相似度 → 返回带引用来源答案 → 若 `is_solved=true` 则不派单。
3. **派单**：调度读取 `RepairOrder + User(师傅) + WorkerSchedule` → 过滤冲突与负载 → 加权打分选师傅 → 更新 `RepairOrder.worker_id / assign_score / assign_reason / status=ASSIGNED` → 更新排班 `cur_orders` → 写 `Notification`。
4. **进度**：师傅每次操作 → 校验状态机合法性 → 更新 `status + version` → 写 `OrderStatusLog` → 推送通知。
5. **评价**：工单 `COMPLETED` → 学生提交 `OrderEvaluation` → 评分 ≥ 4 且 `repair_order.result` 非空 → 知识候选 → 管理员审核 → 入 `knowledge_base`，`source=ORDER`，记录 `source_order_id`。
6. **看板**：从 `repair_order + order_evaluation` 聚合统计维修量、时长、满意度、高频故障 Top 榜。

## 6. 与代码的对应关系

- 实体类：`backend/src/main/java/com/example/backend/entity/`
- 数据访问：`backend/src/main/java/com/example/backend/repository/`
- 数据库表名：小写下划线，如 `repair_order`、`order_status_log`、`worker_schedule`、`knowledge_base`、`order_evaluation`、`notification`
- 字段名：小写下划线，如 `create_time`、`student_id`、`emergency_level`、`appointment_time`
- 注意：`Worker` 不再单独建表，师傅是 `user.role = WORKER`，专长在 `user.specialty`。
