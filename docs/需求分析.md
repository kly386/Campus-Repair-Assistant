# 系统功能分析说明书（需求分析）

> 场景：校园快修的统一入口 + 智能调度中枢。学生一句话 + 一张照片完成报修，系统自动理解故障、分流自助解决或派单、全程跟踪，并把每次维修沉淀为知识资产。

## 1. 系统概述

### 1.1 项目背景

高校宿舍区的日常维修（水电、网络、门窗家具、宿舍电器等）目前普遍依赖线下流程：学生通过微信群、电话或纸质登记本报修，后勤部门人工记录并口头派单。该模式存在以下突出问题：

1. **报修入口分散**：微信群消息滚动快，报修信息易被淹没；电话报修无法留存文字与图片凭证。
2. **信息不完整**：学生描述笼统（"灯坏了"），缺少楼栋、房间号、故障照片等关键信息，师傅需反复沟通确认。
3. **派单靠人工经验**：调度人员需同时权衡师傅专长、排班、位置与工作量，效率低且难以均衡。
4. **进度不透明**：学生无法查询工单状态，只能反复催促；超时工单缺少预警。
5. **知识不沉淀**：相同故障（如"路由器亮红灯"）被反复上门处理，历史维修经验无法复用。

### 1.2 建设目标

| 目标编号 | 目标描述 | 衡量方式 |
|----------|----------|----------|
| G1 | 建立统一在线报修入口，替代微信群 / 电话 / 纸质登记 | 线上报修占比 ≥ 95% |
| G2 | 通过 AI 多模态理解自动补全工单字段，降低学生填写成本 | 故障类别分诊准确率 ≥ 85% |
| G3 | 可自助解决的故障优先分流，减少不必要上门 | 自修解决率 ≥ 30% |
| G4 | 自动匹配师傅并检测时间窗冲突，提升派单效率 | 派单成功率 ≥ 90% |
| G5 | 工单全流程状态可查、变更可追溯 | 状态日志完整率 = 100% |
| G6 | 维修结论回流知识库，形成数据闭环 | 知识入库率 ≥ 60%，分诊准确率持续提升 |
| G7 | 为管理者提供运营数据看板，支撑决策 | 看板覆盖维修量、时长、满意度、高频故障四类指标 |

### 1.3 系统定位

本系统定位为校园后勤维修的**统一入口与智能调度中枢**，而非简单的工单登记工具：

- **统一入口**：学生、维修师傅、管理员三类角色在同一平台协作，数据互通。
- **智能理解**：以 AI 多模态能力替代人工填写与人工分类，把非结构化描述转为结构化工单。
- **智能分流**：优先自助诊断，能自修则不派单，降低后勤上门压力。
- **智能调度**：以规则引擎 + 加权打分替代人工派单，兼顾专长、时间、距离与负载。
- **数据闭环**：每一次维修的评价与结论回流知识库，使系统随使用而持续变聪明。

## 4. 非功能需求

### 4.1 性能需求

| 需求编号 | 需求项 | 指标要求 |
|----------|--------|----------|
| NFR-P-01 | 页面首次加载时间 | ≤ 3 秒（校园网环境） |
| NFR-P-02 | 普通接口响应时间 | 95% 请求 ≤ 1 秒 |
| NFR-P-03 | AI 多模态分诊响应时间 | ≤ 8 秒；超时则异步回填，不阻塞工单提交 |
| NFR-P-04 | RAG 问答响应时间 | ≤ 10 秒 |
| NFR-P-05 | 并发能力 | 支持 ≥ 200 名学生同时在线报修 |
| NFR-P-06 | 看板统计查询 | ≤ 3 秒（数据量 10 万工单以内） |

### 4.2 安全需求

- 密码 BCrypt 加密存储；JWT 令牌认证并设置合理过期时间。
- 按 STUDENT / WORKER / ADMIN 三类角色做接口级鉴权；学生只能看本人工单，师傅只能看本人工单。
- 参数校验防 SQL 注入与 XSS；手机号等敏感信息脱敏展示；AI 服务密钥经环境变量注入，禁止硬编码。

### 4.3 可靠性需求

- 状态流转幂等：重复提交拦截率 100%，不产生重复工单或重复流转。
- 派单与状态更新采用乐观锁，避免并发覆盖。
- 状态流转日志完整率 100%，任何状态变更均可追溯。
- AI 服务不可用时，报修流程仍可正常提交，字段由学生手工填写（服务降级）。
- 数据库每日备份，支持按时间点恢复。

### 4.4 易用性需求

- 从进入报修页面到提交成功不超过 3 步；学生端适配手机浏览器，支持拍照上传。
- AI 识别结果需回显给学生确认，允许人工修正。
- 工单当前状态与下一步操作一目了然；错误提示指明具体原因与修正方式。

### 4.5 关键质量指标

| 指标名称 | 计算方式 | 目标值 |
|----------|----------|:------:|
| 分诊准确率 | 类别预测正确数 / 测试集总数 | ≥ 85% |
| 自修解决率 | is_solved=true 会话数 / 总会话数 | ≥ 30% |
| 分流正确率 |（该自修分到自修 + 该派单分到派单）/ 总数 | ≥ 85% |
| 派单成功率 | 成功派单数 / 总工单数 | ≥ 90% |
| 状态日志完整率 | 有日志的状态变更数 / 总变更数 | 100% |
| 重复提交拦截率 | 被拦截的重复请求数 / 重复请求总数 | 100% |
| 知识入库率 | 审核通过数 / 候选数 | ≥ 60% |

### 5.2 工单状态机

```
SUBMITTED → ASSIGNED → ON_THE_WAY → PROCESSING → PENDING_ACCEPT → COMPLETED
     └→ CANCELLED            └→ RESCHEDULED（改约）
```

| 状态 | 中文名 | 说明 |
|------|--------|------|
| SUBMITTED | 待派单 | 学生已提交，等待调度 Agent 派单 |
| ASSIGNED | 已派单 | 已匹配到师傅，等待师傅接单 |
| ON_THE_WAY | 上门中 | 师傅已接单，正在赶往现场 |
| PROCESSING | 处理中 | 师傅正在维修 |
| PENDING_ACCEPT | 待验收 | 师傅维修完毕，等待学生确认 |
| COMPLETED | 已完成 | 学生确认验收（终态） |
| CANCELLED | 已取消 | 工单被取消（终态） |
| RESCHEDULED | 已改约 | 改约中间态，由已派单（ASSIGNED）进入，改约后触发重新派单 |

允许的状态流转：

| 原状态 | 允许流转到 |
|--------|------------|
| SUBMITTED | ASSIGNED, CANCELLED |
| ASSIGNED | ON_THE_WAY, CANCELLED, RESCHEDULED（改约） |
| ON_THE_WAY | PROCESSING, CANCELLED |
| PROCESSING | PENDING_ACCEPT, CANCELLED |
| PENDING_ACCEPT | COMPLETED, PROCESSING（驳回返修） |
| COMPLETED | ——（终态） |
| CANCELLED | ——（终态） |
| RESCHEDULED | ASSIGNED（重新派单成功）、SUBMITTED（重新派单失败）、CANCELLED |

### 5.3 核心枚举

- 角色 Role：STUDENT / WORKER / ADMIN
- 工单状态 OrderStatus：SUBMITTED / ASSIGNED / ON_THE_WAY / PROCESSING / PENDING_ACCEPT / COMPLETED / CANCELLED / RESCHEDULED
- 紧急程度 EmergencyLevel：LOW / MEDIUM / HIGH
- 排班时间段 TimeSlot：MORNING / AFTERNOON / EVENING
- 排班状态 ScheduleStatus：FREE / BUSY / REST
- 知识来源 KnowledgeSource：MANUAL / ORDER
- 通知类型 NotificationType：ORDER_STATUS / SYSTEM / REMIND

## 6. 接口需求

- 基础路径 `/api`，RESTful 风格，统一响应格式 `{ "code": 200, "message": "success", "data": {...} }`。
- JWT 令牌认证，角色鉴权 STUDENT / WORKER / ADMIN。
- 后端分层：Controller → Service → Repository；字段命名前端 camelCase、数据库 snake_case，由 JPA 自动映射。

已实现（脚手架阶段）：工单 CRUD（`POST/PUT/GET/DELETE /api/orders...`）。

## 7. 验收要点

- 智能报修：输入"3号楼302灯不亮"+照片，正确识别为水电维修类并补全楼栋房间。
- 分诊准确率：100 条标注样本上类别预测准确率 ≥ 85%。
- 自助诊断：提问"路由器亮红灯怎么办"返回带引用来源的解答；相似度 < 0.7 时引导报修。
- 派单：结果与师傅专长匹配且不与既有工单时间冲突；有可用师傅时派单成功率 ≥ 90%。
- 状态机：非法流转（如 COMPLETED → PROCESSING）被拒绝；同一幂等键重复提交 10 次仅生成 1 条工单；状态日志完整率 100%。
- 评价与沉淀：评分 ≥ 4 且结论非空进入候选，审核通过后入库；评分 < 4 或未审核的结论不进入知识库。
- 看板：正确展示维修量、平均响应/完成时长、满意度、高频故障 Top 榜。
- 权限：学生无法访问管理员接口、无法查看他人工单。
- 部署：Docker Compose 一键启动 mysql、backend、frontend 三个服务。
