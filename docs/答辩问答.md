# 答辩问答预案（文件模块 / 协议相关）

> 用途：答辩前自己过一遍。按"老师问题 → 你答"的形式组织，答案都对应本项目已实现代码。

---

## Q1：分片上传，如果第 4 片先到、不是顺序到达，怎么重组？

**答**：重组不依赖到达顺序，靠切分时就编好的序号。前端用 `File.slice()` 把文件切成 5MB 一片，每片带 `chunkIndex`（从 1 起）；后端收到一片就调 OSS SDK 的 `uploadPart`，**OSS 按 partNumber 存储元件，到达顺序无关**。完成后调 `complete`，OSS 会按 partNumber 升序把所有元件拼回原文件。

- 代码位置：`service/impl/FileStorageServiceImpl.java` → `initMultipartUpload / uploadMultipartChunk / completeMultipartUpload`
- 类比：收快递不用按单号顺序到齐，拼箱看"第几箱/共几箱"

**延伸**：正因为按编号补偿，哪片失败只需重传那一片 → **断点续传**的原理。

## Q2：为什么小文件不能一个一个传？1KB 文件的网络浪费在哪？

**答**：单请求的隐形开销（TCP 握手、TLS 握手、请求头、连接排队、线程创建、逐条事务提交）远大于 1KB 本身。传 1000 个 1KB 文件逐个传 = 1000 次往返，网络利用率可能不到 10%。

**我的方案**（`POST /api/files/batch-upload`）：
1. 一次 HTTP 请求带 N 个 `MultipartFile`（一次往返）
2. 元数据 **一条多行 VALUES 的 INSERT** 批量落库，而不是 N 次单行提交（一次数据库往返）
3. 配合 JWT/会话等头信息也只带一次

**结论**：把 N 次网络/数据库往返合并成 1 次，这就是批量上传的意义。

## Q3：现在这套系统走的是什么协议？

| 层 | 协议 | 说明 |
|---|---|---|
| 应用层 | HTTP/1.1（本地 5173→8080）；HTTPS（后端→阿里云 OSS 443） | 分片/批量上传用 multipart/form-data；下载走 HTTP 流式响应或签名 URL |
| 传输层 | **TCP** | HTTP 与 HTTPS 都建立在 TCP 上，可靠有序——文件一字不能丢 |
| 链路层等 | 以太网/IP（不展开） | |

**追问预案**：
- "为什么不用 UDP？" → 文件/数据必须不丢不乱序 → TCP；UDP 用于音视频流（丢几毫秒没问题）
- "HTTP/1.1 还是 2？" → axios/浏览器自动协商，本项目默认 HTTP/1.1；关键点在于**无论 1.1/2，语form上传都是同样的 multipart 语义**

## Q4：实时聊天工具（微信/QQ / 在线客服）文件传输走什么协议？Windows 编程里相关的是什么？

（注：老师口述 "wenshort" 应为 **WebSocket**）

| 场景 | 报文协议 |
|---|------|
| 传统客户端（微信/QQ 老式传文件） | **私有 TCP 二进制协议**（自研，非 HTTP），并支持 P2P 直连打洞 |
| 网页在线客服 | 聊天消息走 **WebSocket**（HTTP Upgrade 之后的长连接，服务器可主动推）；文件本身走 **HTTP POST**（常见做法：先传对象存储拿 URL，再把 URL 通过 WebSocket 消息推给对方） |
| 浏览器 P2P 大文件直传（可选） | **WebRTC Data Channel**，建立在 **UDP + SCTP** 上 |
| Windows 编程对应 | **Winsock**（socket/connect/send/recv）——WebSocket、HTTP、私有 TCP 协议都是 TCP 字节流之上的应用层封装 |

**底层模型**：TCP 给的是"可靠字节流"，没有"消息"概念；HTTP / WebSocket / 私有协议都是在字节流上定义**消息边界和格式语义**。

## Q5（进阶追问）：如果要给维修助手加"在线客服"，怎么做？

**答**：三步、复用现状即可：
1. **聊天消息** → 后端加 WebSocket 端点（Spring Boot 提供 `spring-websocket`），学生和维修师傅互发文字，服务器能即时推
2. **聊天里发图/发工单附件** → 直接复用现有 OSS 上传链路，消息体只发 `{"type":"image","url":...}` 字符串
3. **将来真要浏览器对浏览器传超大文件** → 再升级 WebRTC Data Channel；不需要就没必要引入

**要点**：WebSocket 只替换"消息推送通道"，文件存储继续用我们已做好的分片/批量 OSS 体系——两套能力正交。

## 现场演示话术（30 秒版）

> "大文件按 5MB 分片，带序号传 OSS，服务端按序号合并——片几时到没关系，天然断点续传；
> 小文件一次请求批量传，元数据一条多行 VALUES 批量落库——合并网络往返；
> 全程 HTTP over TCP，文件本体在阿里云 OSS 私有 Bucket，本地 MySQL 只存元数据；
> 若加在线客服，消息走 WebSocket 长连接，文件传输还是复用这套 OSS 方案。"
