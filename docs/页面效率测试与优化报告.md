# 页面效率测试工具选型与优化报告

> 任务：找一个小组内通用的页面效率测试工具，对页面进行优化，并针对页面优化技术的问题提出相应解决方案。
> 被测页面：运营数据大屏 `frontend/src/views/Dashboard.vue`（路由 `/dashboard`）。


---

## 一、结论先行

1. **工具选 Lighthouse（Chrome DevTools 内置面板）**，全组统一使用，零安装、口径一致、报告可导出；WebPageTest 作为跨网络对比备选，DevTools Performance 作为主线程长任务分析备选。
2. **必须在生产构建下测**（`npm run build` + `npm run preview`），不能在 `npm run dev` 下测，否则未压缩、未 tree-shaking、HMR 注入会让分数失真。
3. **必须带着登录态测**：大屏在鉴权之后，直接扫码/直接访问 `/dashboard` 只会被重定向到登录页，测到的是登录页而不是大屏。
4. 本次已落地 7 项优化（ECharts 按需打包、图表实例与销毁、后台暂停轮询、resize 节流、构建产物拆包、preview 代理、Nginx gzip + 静态资源长缓存）。
5. 动手前组内先核对了几种常见的优化说法，筛掉 5 处会直接写错结论的做法（测试环境、FID/INP、`v-lazy`、`v-once`、"vite 配置静态资源缓存"），正确口径见第三节。

---

## 二、工具选型：为什么是 Lighthouse

| 工具 | 形态 | 优点 | 局限 | 结论 |
|------|------|------|------|------|
| **Lighthouse** | Chrome DevTools 面板 / `npx lighthouse` CLI | 组员浏览器自带；性能、最佳实践、SEO 一套标准；可导出 HTML/JSON；有明确的优化建议 | 实验室数据，不等于真实用户；桌面/移动预设不同 | **小组首选** |
| WebPageTest | 在线 | 多地点、多网络、多浏览器；可看加载瀑布图与视频 | 需要上传/内网穿透，隐私与网络条件受限 | 对比备选 |
| DevTools Performance | Chrome 面板 | 火焰图定位长任务、布局抖动、ECharts 渲染耗时 | 没有 0–100 分，不适合统一横向对比 | 定位问题专用 |
| 商业 APM / RUM | SaaS | 真实用户数据、告警 | 收费、接入成本高 | 不采用 |

**小组统一口径（照此执行，数据才可横向比较）：**

1. 同一 Lighthouse 大版本、同一 Chrome 版本，测试前记录版本号。
2. 无痕窗口、禁用所有扩展、关闭其他标签页；窗口固定 1920×1080、100% 缩放。
3. 设备选 **Desktop**（大屏是 PC 端）；Desktop 预设默认 CPU 不降速、仅轻度网络节流。若要模拟弱网，必须全组统一并记录节流参数，不要只口头说"Fast 3G"。
4. 同一页面连测 3 次，取中位数；每次测试前清理浏览器缓存。
5. 至少产出两份报告：优化前 `lighthouse-before.html`、优化后 `lighthouse-after.html`，随实验报告一起归档。

## 三、常见优化做法的核对与取舍

| 常见说法 | 结论 | 理由与处理 |
|----------|------|------------|
| 选 Lighthouse，小组统一使用 | 采用 | 与本文选型一致 |
| 无痕模式、关闭插件、固定窗口、统一设备 | 采用 | 已写入测试口径 |
| 访问 `npm run dev` 的 `localhost:5173` 测 | 不采用 | dev 下模块未压缩、未 tree-shaking，还带 HMR 运行时；Lighthouse 分数会明显偏低。必须 `npm run build` + `npm run preview` 后测 |
| 指标看 LCP / FID / CLS | 修正 | FID 已于 2024 年 3 月被 INP 取代；且 Lighthouse **实验室**报告只给 TBT（总阻塞时间），不给 INP。INP 要看真实用户数据或 Performance 面板实测，不能写"Lighthouse 测得 INP=xx ms" |
| 报告看 LCP / 交互延迟 / CLS 三项 | 修正 | 实验室口径应写 **FCP、LCP、TBT、CLS、Speed Index**；INP 单独注明来源 |
| 图片转 WebP、`v-lazy` 懒加载、压缩原图 | 不适用 | 大屏没有任何 `<img>` 资源，Logo 是 CSS 渐变；且 `v-lazy` 不是 Vue 内置指令，需额外引入第三方库。写进报告会与代码对不上 |
| ECharts 全量引入体积大，改按需引入 | 采用并已实施 | 见第五节第 1 项 |
| 页面一次性请求全部接口，建议拆分 / 延迟请求 | 部分修正 | 当前 `/api/dashboard/overview` 是聚合接口，拆成 9 个请求反而增加 RTT。真正问题是返回了前端未使用的 `roles`、`files`，且一次要跑 9 条 SQL，应"按需返回 + 短 TTL 缓存"，而不是盲目拆分 |
| 定时轮询改为页面隐藏时暂停 | 采用并已实施 | 见第五节第 3 项；轮询间隔保持 30s 符合大屏业务 |
| 布局跳动 CLS 高，图表容器固定宽高 | 修正 | `.chart` 已是固定 `height: 300px`（Dashboard.vue L280-282），实测 CLS 应接近 0，不要把 CLS 当成本项目的主要优化点 |
| Vite 配置静态资源缓存 | 不采用 | 开发服务器不做缓存；Vite 产物文件名本身带 hash，真正的缓存策略在 Nginx/CDN。已改为 Nginx `expires 1y` + `index.html` 不缓存 |
| 指标卡用 `v-once` 静态化 | 不采用 | 指标卡每 30 秒随接口更新，`v-once` 会让数值永远停在首帧，属于功能性错误 |
| 用 `computed` 缓存计算值 | 收益可忽略 | 大屏只有少量数组映射，计算成本远小于渲染与网络 |
| 补充项：生产构建、登录态、ECharts 事件/实例销毁、gzip | 已补充 | 已写入本报告与代码 |

## 四、统一测试流程（修正版）

### 4.1 前置条件

```bash
# 1) 启动后端（默认 8081）
cd backend
mvn spring-boot:run

# 2) 生产构建并本地预览（不要用 dev）
cd frontend
npm run build
npm run preview        # 默认 http://localhost:4173
```

`vite.config.js` 已为 `preview` 复用与 `dev` 相同的 `/api`、`/ws` 代理，保证预览环境能取到大屏数据。

### 4.2 跑 Lighthouse

1. Chrome 无痕窗口访问 `http://localhost:4173`，**先完成登录**并进入运营看板。
2. `F12` → `Lighthouse` 面板：
   - 模式：Navigation；设备：Desktop；
   - 勾选 Performance、Best Practices、SEO（Accessibility 可选）；
   - 点击「Analyze page load」，等待完成。
3. 右上角导出 HTML/JSON，命名 `lighthouse-before.html`。

> **登录态说明**：DevTools 的 Lighthouse 在"当前标签页"运行，会复用登录 Cookie/localStorage，所以能测到真实大屏；如果用 CLI 且未注入凭证，只会测到被重定向后的登录页，数据无效。

## 五、已实施的页面优化（代码级）

| # | 问题 | 优化动作 | 代码位置 | 预期影响 |
|---|------|----------|----------|----------|
| 1 | `import * as echarts from 'echarts'` 全量打包 | 改为 `echarts/core` + 按需注册折线/饼/柱 3 种图表、Grid/Tooltip/Legend/AxisPointer 4 个组件、Canvas 渲染器 | [Dashboard.vue](../frontend/src/views/Dashboard.vue#L62-L83) | 显著减小大屏路由 JS 体积，降低解析与执行时间 |
| 2 | 图表实例用 `el.__key` 临时属性管理，容易取到同一实例 | 改为 `Map` + 固定业务 key（trend/status/...），统一 `init/dispose` | [Dashboard.vue](../frontend/src/views/Dashboard.vue#L200-L230) | 消除隐式共享实例的隐患，路由切换不泄漏 |
| 3 | 30s 轮询在后台标签页继续请求 | `document.hidden` 时跳过轮询；`visibilitychange` 切回立即补一次 | [Dashboard.vue](../frontend/src/views/Dashboard.vue#L211-L235) | 减少无意义请求与后端压力 |
| 4 | 窗口 resize 直接重绘全部图表 | 150ms 节流 + 卸载时清理定时器 | [Dashboard.vue](../frontend/src/views/Dashboard.vue#L237-L243) | 拖动窗口不卡顿，避免高频重绘 |
| 5 | 第三方大依赖混在入口 chunk | Rollup `manualChunks` 拆出 `vue` / `element-plus` / `echarts` 三个稳定 chunk，其余依赖仍跟随懒加载路由按需下载 | [vite.config.js](../frontend/vite.config.js#L26-L41) | 重复访问命中缓存，且不破坏登录页等路由的按需加载 |
| 6 | `vite preview` 没有代理，生产构建无法取数 | 抽出 `createProxy()`，`server` 与 `preview` 共用 | [vite.config.js](../frontend/vite.config.js#L4-L25) | 让"生产构建 + 本地预览"的性能测试可行 |
| 7 | 部署后静态资源无压缩、无长缓存 | 开启 gzip；hash 资源 `expires 1y, immutable`；`index.html` 不缓存 | [nginx.conf](../frontend/nginx.conf#L6-L31) | 降低传输体积，二次访问更快，发布后仍能拿到新入口 |

### 尚未实施、建议后续排期

- **Element Plus 按需引入**：当前 `main.js` 全量 `app.use(ElementPlus)` 并引入全量 CSS，是首屏 CSS/JS 的大头。需引入 `unplugin-vue-components` + `unplugin-auto-import` 或手工按需注册，改动面覆盖全部页面，适合单独一个迭代做。
- **大屏图表懒渲染**：6 个图表在首屏同步 `setOption`。可用 `IntersectionObserver` 只渲染视口内图表，降低首屏主线程压力（TBT）。
- **接口瘦身与缓存**：`/dashboard/overview` 返回的 `roles`、`files` 前端未用；建议按需返回，并对聚合结果做 10–30s 服务端缓存，减少 9 条 SQL 的重复执行。
- **骨架屏**：首屏数据返回前用灰块占位，提升感知性能（注意占位高度需与最终布局一致，避免引入 CLS）。

## 六、页面优化技术问题与解决方案（任务核心问答）

| 技术问题 | 典型表现 | 根因 | 解决方案 | 本项目落地 |
|----------|----------|------|----------|------------|
| JS 体积过大 | 首屏下载/解析慢、TBT 高 | 全量引入组件库/图表库 | tree-shaking、按需注册、路由懒加载、`manualChunks` | ECharts 按需 + 路由已懒加载 + 拆包已做；Element Plus 按需列为后续 |
| 长任务阻塞主线程 | 点击无响应、TBT 高 | 一次性同步渲染大量图表/大列表 | 分批渲染、`requestIdleCallback`、虚拟列表、Web Worker | 图表懒渲染列为后续 |
| LCP 偏慢 | 主内容出现晚 | 首屏 JS 大、接口慢、渲染链长 | 减小首屏 JS、接口聚合、骨架屏、关键资源预加载 | 已减小图表 JS；接口已是聚合接口 |
| CLS 布局偏移 | 图表/卡片加载时跳动 | 容器无固定尺寸、异步内容撑开布局 | 容器固定宽高、字体 `font-display`、占位骨架 | 图表容器已定高 300px，CLS 风险低 |
| 轮询浪费请求 | 后台标签持续请求、后端压力大 | 定时器不感知页面可见性 | `document.hidden` 跳过、`visibilitychange` 补偿、按需拉长间隔 | 已实施 |
| 事件/实例泄漏 | 页面切多次后内存上涨、越切越卡 | `resize` 监听、定时器、ECharts 实例未销毁 | `onBeforeUnmount` 统一清理，`dispose + clear` | 已实施 |
| 静态资源重复下载 | 二次访问仍全量下载 | 无缓存策略 / 文件名无 hash | 文件名 hash + 长缓存 + 入口 HTML 不缓存 | Nginx 已配置 |
| 传输体积大 | JS/CSS 下载慢 | 未压缩 | gzip/brotli、CDN | Nginx gzip 已配置 |
| 接口粒度不合理 | 请求数多或单次过重 | 过度拆分或过度聚合 | 按页面聚合、按需字段、服务端短缓存 | 建议按需返回 + 缓存 |
| 缺少持续监控 | 优化后回退无人发现 | 只做一次性测试 | Lighthouse CI 门禁、`web-vitals` 上报 | 建议后续接入 |

## 七、复测与验收标准

1. 按第四节在同一环境复测，产出 `lighthouse-after.html`。
2. 验收看三项：
   - Performance 得分提升且不低于 80（桌面）；
   - LCP ≤ 2.5s、CLS ≤ 0.1、TBT ≤ 200ms（桌面实验室口径）；
   - 后台标签 30s 内 `/api/dashboard/overview` 请求数由 1 降为 0。
3. 报告附：优化前后截图、Network 体积对比、关键代码 Diff。
4. 若分数未达预期，用 DevTools Performance 录一次加载，按火焰图定位长任务，再决定是继续拆包还是做图表懒渲染。

## 八、答辩/评审常见追问

- **为什么选 Lighthouse？** 组员浏览器自带、口径统一、报告可导出；其他工具定位不同（WebPageTest 偏多网络对比，Performance 偏长任务定位）。
- **为什么不能在 dev 下测？** dev 不压缩、不 tree-shaking、带 HMR 运行时，测出来的是"开发态"，不能代表上线效果。
- **FID 和 INP 是什么关系？** FID 已被 INP 取代；Lighthouse 实验室给 TBT，INP 需要真实用户数据或 Performance 面板。
- **ECharts 按需引入为什么能变小？** `echarts/core` 只含渲染内核，图表与组件通过 `use()` 显式注册，未注册的代码会被 tree-shaking 删除。
- **接口为什么不做拆分？** 大屏是一次性聚合展示，拆成多个请求会增加 RTT；正确方向是减少冗余字段与服务端缓存。
- **CLS 为什么低？** 6 个图表容器都固定 `height: 300px`，数据到达前后布局不变。
